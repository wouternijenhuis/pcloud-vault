# pCloud Vault format 1

This is a new application protocol, not an independently audited encryption product. The RustCrypto implementations supply the primitives; correctness of the storage, merge and recovery protocol still needs independent review. Do not use it as the sole copy of important data during validation.

## Files and key hierarchy

`vault.json` is a bounded, public JSON header with `formatVersion`, random 128-bit `vaultId`, Argon2id parameters, a random 128-bit salt, `wrappedKey`, and `keyCheck`. Password bytes are UTF-8 without implicit normalization. Argon2id version 0x13 derives a 256-bit wrapping key. New production vaults use 262144 KiB memory, three iterations and one lane. Imported parameters are rejected before derivation unless memory is 65536–524288 KiB, iterations 3–10 and lanes 1–8. Test-only fixtures permit 8192 KiB; public production creation never selects that setting.

The root key is 256 random bits from the operating-system CSPRNG. `wrappedKey` is the root key encrypted with XChaCha20-Poly1305. Associated data is the UTF-8 JSON encoding of the tuple `["pcloud-vault/key-envelope",formatVersion,vaultId,kdf,salt]` (Rust/Serde compact encoding and the field order shown in `KdfParams`). `keyCheck` encrypts the exact 16 bytes `vault-key-check!` under the root key with the compact JSON tuple `["pcloud-vault/header-authentication",formatVersion,vaultId,kdf,salt,wrappedKey]` as associated data. This authenticates the entire password envelope when a remembered/recovery key is used, so copying an old key check onto altered wrapping settings is rejected. Both envelopes are hex-encoded `24-byte nonce || ciphertext || 16-byte tag`.

HKDF-SHA256 with salt `pcloud-vault/v1` and distinct `metadata` and `local-checkpoint` info values derives 256-bit metadata and checkpoint keys from the root key. The implementation zeroizes root keys, derived wrapping keys, file keys on manifest destruction, and plaintext cryptographic buffers. It cannot guarantee erasure from operating-system paging, external applications, or all serializer allocations.

`objects/<random-128-bit-lowercase-hex-id>.obj` contains one kind byte (`1` chunk, `2` manifest, `3` commit), followed by an XChaCha20-Poly1305 envelope. A cloud `ReplicationObject` carries the ID, textual kind (`chunk`, `manifest`, `commit`) and envelope bytes **without** the disk kind byte. Object IDs are random, never plaintext hashes or filenames. Existing IDs cannot be replaced with different bytes.

Manifest and commit associated data is UTF-8 `pcloud-vault/v1/<vaultId>/<kind>/<objectId>`. Their plaintext is JSON, encrypted using the metadata key. Their size is limited to 64 MiB. Unknown object kinds, invalid IDs and oversized objects are rejected. Metadata is authenticated before deserialization. Object paths never use user names or unvalidated IDs.

## File versions

Every version has a fresh random 256-bit file key and random 128-bit version ID. The manifest contains the stable original file ID, version ID, total size, file key, and ordered array of `{id,length}` chunk references. Non-final chunks are exactly 4 MiB; the last chunk is the remaining length. Empty files have no chunks. Maximum supported file size is 1 TiB. The authenticated manifest binds count, order and length; duplicate chunk IDs and inconsistent size/count are rejected.

Chunk encryption uses the file-version key and a fresh random 192-bit nonce. Associated data is the compact JSON tuple `["pcloud-vault/v1/chunk",vaultId,fileId,versionId,objectId,index,length]`, with zero-based integer index and plaintext length. Moving ciphertext to another file, version, index or object ID fails authentication. No chunk is returned until its tag and length have been checked.

Random writes and truncation produce a new file version, reading and re-encrypting one 4 MiB chunk at a time. Gaps are zero-filled. This gives bounded memory and simple nonce safety; it costs a complete version rewrite, so large frequently edited files are a known performance tradeoff. Manifests, original names and directory relationships remain encrypted. An ordinary decrypted export is explicit and never overwrites an existing destination.

## Immutable journal and multi-PC merge

An encrypted commit has random `id`, causal `parents`, random `deviceId`, millisecond `modified` timestamp, and one operation: create, write, rename, move, relocate, trash or restore. Parent IDs describe causality, not wall-clock ordering. Timestamps are for display only. Uploads must publish all chunk dependencies before a manifest and all manifest/parent dependencies before a commit. The core exposes pending IDs in that dependency order.

`relocate` is the atomic Windows rename/move/replace primitive. Its single encrypted operation contains source stable `id`, destination `parent` and `name`, and optional `displaced` target ID. Both source location changes and target trash occur in one causal commit; there is no durable intermediate state that removes the old document before moving the temporary replacement. Destination collision, Windows-name, folder-kind and descendant-cycle checks run before publication. Replacement of folders, or a folder over a file, is rejected. Replaced file ciphertext/history stays in trash. Concurrent edits to a displaced target survive through the normal delete/edit conflict rules. Preparatory materialization of already exposed aliases may add preservation commits, but never renames or trashes either side before the atomic relocation itself.

Clients retain every commit and tombstone. Commits with unavailable parents or manifests are deferred; metadata can be accepted without cached chunks. Missing chunks produce `OfflineUnavailable`, allowing the transport to fetch them on demand. A metadata-only replica is therefore usable without downloading file contents.

The deterministic reducer processes causal order, with lexicographic commit-ID order among ready commits. Names, parent locations, contents and deletion state are independent causal multi-value registers; observing one branch does not silently overwrite another branch. Causal successors replace their predecessors. Concurrent content versions become visible conflict copies with deterministic derived IDs. Concurrent rename/move alternatives become deterministic location-conflict aliases. Before any subsequent local mutation or incoming replication can supersede an exposed alias, the client durably materializes it as an immutable Create commit with that same stable ID, content and location. This preserves an already exposed conflict through later primary writes, renames, moves and sync; it remains until the user explicitly trashes/resolves that copy. Independent materializations with the same ID merge through the same causal registers. Such preservation commits are ordinary encrypted pending changes and are replicated in causal order. An edit concurrent with deletion survives. Once a deletion observes all live edits it hides the file; restore makes it visible again.

Concurrent folder moves can form a cycle even when each local move was valid. The smallest stable ID in each cycle is deterministically recovered at the root. Missing, non-folder and deleted parents recover live children at the root. Windows case-insensitive sibling-name collisions receive deterministic conflict suffixes. All generated names are bounded to 240 UTF-16 code units without splitting a surrogate pair. Collision disambiguation uses full stable IDs and a bounded ordinal search rather than unbounded suffix growth. A user editing a derived conflict first materializes it as a normal stable entry; original immutable versions remain recoverable.

Every immutable file is written to a randomly named temporary file, flushed with `sync_all`, then renamed to its final ID. Publishing the encrypted commit is the durable write journal. `local.bin` is an encrypted checkpoint containing this PC's device ID, pending object IDs, favorites, offline pins, cache limit and observed committed history. Checkpoint replacement keeps a previous encrypted copy until the replacement is published. On restart, new journal commits from the local device reconstruct missing pending records.

The core holds an exclusive process lock in `vault.lock` while open. A single desktop mutex additionally serializes the filesystem and UI. Successful mutations acknowledge durable local writes; they do not assert cloud durability. The transport must distinguish local and uploaded state and acknowledge objects only after verification. File flushing does not protect against all filesystem/controller failures; keep independent backups.

Favorites and offline pins are per-PC encrypted preferences. Pinned folders protect their descendants. Cache eviction removes only acknowledged, unpinned chunk objects; metadata/history is retained. Chunks referenced by any pending commit or manifest stay protected even when the chunk upload itself has already been acknowledged. The cache limit is soft when protected data exceeds it. Eviction order is deterministic object-ID order, not LRU. Automatic remote garbage collection is intentionally absent.

## Passwords and recovery

Changing the password authenticates the old envelope, generates a fresh salt, and rewraps the same root key. `prepare_password_change` returns the authenticated new header without mutating disk or memory. This permits the desktop to durably journal the pending cloud header first, then `adopt_header` it locally, publish and verify the remote wrapper, and finally clear that pending journal. `adopt_header` authenticates the entire header with the current root key and rejects different vault IDs or tampered envelopes before changing disk or memory. File ciphertext does not change. All PCs must receive the updated header through the application's credential-change coordination. Merely rewrapping the key does not revoke an unlocked PC or invalidate old header copies held in cloud history. True revocation requires a fresh vault/root key and data migration.

The offline recovery string is `PV1-<vaultId>-<64-lowercase-hex-root-key>`. It is equivalent to the full vault key and must be handled as a secret. It cannot replace missing ciphertext, manifests or commit history. A recovery export uses exclusive file creation and refuses existing paths. The desktop stores remembered root keys separately through current-user Windows DPAPI; the core never stores the password.

## Protection boundaries

The vault protects content and names against disclosure by cloud storage, and detects ciphertext tampering. The provider still sees encrypted object sizes, counts, upload timing, access patterns, vault format, and key-derivation settings. Unlocked Windows sessions, malware running as the user, screen capture, external application caches, paging, backups of plaintext originals and explicit exports are outside the guarantee.

The encrypted local checkpoint detects removal of previously observed commits. A provider can still withhold new changes, deny service, fork views, or replay an entire old vault and checkpoint onto a fresh PC. Encryption alone cannot prove freshness to a new device without an independent trusted checkpoint. There is no server-side password reset, no implied protection for ordinary unencrypted pCloud files, and no compatibility with pCloud Crypto or Cryptomator.

Cryptographic test-vector source: [XChaCha draft, Appendix A.1](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-xchacha-03#appendix-A.1). This is a published vector, not a claim that XChaCha has an IETF RFC standard.
